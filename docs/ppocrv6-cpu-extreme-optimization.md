## 一、直接结论（四大核心问题总览）

| 核心问题 | 第一性原理判断（面向 29 号机 Xeon Silver 4216） | 可判定的工程动作 |
|---|---|---|
| **1. ONNX 模型与 ORT 还有多少空间？上限是多少？** | **仍有明显空间，但要区分“输入/算子工作量”与“引擎算力上限”**。`29` 实测当前 `ORT 1.20.1 FP32` 在 `small DET (736×992)` 上仅跑出 `50.7 GFLOPS`（2 核实测 SGEMM 天花板 `~95 GFLOPS` 的 `53%`），存在布局重排（`12.2%`）与未融合 `GELU`（`7.7%`）。此外，工作量本身存在两大可削减项：稀疏宽条图（如 `806×187`）在 `min=736` 下被放大 15.5 倍面积；密集图 `REC` 在 `minW=320` 下存在显著补零浪费。**当前不预先承诺整页加速倍数**，最终上限须在 29 上用配对数据集实测交付三组数（4 核最低 P95、4 核最大持续 RPS、16 物理核扩展上限）。 | ① 稀疏图比 `DET min=736/640`；② 密集图比 `REC minW=320/160`（需人工真值裁决变化行）；③ 评估 `AVX-512 VNNI` 静态 INT8。 |
| **2. PP-OCRv6 用 ORT 做 CPU 推理是最好的吗？** | **不是普遍赢家，且在 Xeon 4216 上存在更优候选**。官方 Xeon 8350C 实测中，`small` 的 ORT (`0.61s`) 与 OpenVINO (`0.59s`) 接近，但 `medium` 差距达 `2.36×`（`3.31s` vs `1.40s`）；`RapidOCRLite exact` 在 x86 AVX-512 上对 `small DET` 测得 `2.08×`（整图 `1.90×`）无损提速。4216 具备 `AVX-512_VNNI`（唯一 4× 硬件倍率，**无 BF16/AMX**），**原生 OpenVINO CPU（FP32 及 NNCF 精度受控 INT8）** 与 **`RapidOCRLite exact`** 是第一梯队候选；`DET` 与 `REC` 甚至可分别选型。 | 同权重 SHA、同 4 核配额下，隔离对比：现网 ORT 1.20.1 vs 新版 ORT vs 原生 OpenVINO FP32 vs `RapidOCRLite exact`（附 Paddle oneDNN 参考），再测 OpenVINO NNCF INT8 与 ORT S8S8 QDQ。 |
| **3. 自研定制 / Rust 是否更好？** | **按阿姆达尔定律，仅换 Rust 壳调同一 ORT 不能大幅降单图延迟**。`29` 实测 `00009282.jpg` 上神经网络推理占 `96.1%`（非模型代码仅 `3.9%`），本地表格与密集文档样图上非模型占比同样仅 `4% ~ 5%`——完全消除胶水层最多快 `1.04× ~ 1.05×`。纯 Rust 通用推理库（`tract`）算子性能不如 oneDNN；只有**专用 SIMD 内核**（如 C++ `RapidOCRLite`、纯 Rust `qppocr`）才能改变网络耗时。Rust/C++ 真正的系统价值在于**单进程共享权重 + 多并发请求队列**以压低 4 GiB 约束下的双进程内存翻倍，但**应先在 Python OpenVINO `AsyncInferQueue` 验证单进程共享收益**，再决定是否投入 Rust 重写。 | 先在 Python 侧用 `OpenVINO AsyncInferQueue` 验证单进程共享模型与内存下降；若再需原生内核，先拿 `RapidOCRLite exact` 与 `qppocr`（先核对字典 SHA！）做第三方对照，按 Profile 决定是否自写热点。 |
| **4. 全网 PP-OCRv6 现成框架与变种模型是否有更优解？** | **公开检索未找到在中文通用/试题场景下，同时证明比官方 `small` 更准且更快的现成第三方派生权重**（公开 INT8 预制包 `RustO` / `Circulus` 存在 REC 未全量化、静态 640² 破坏长图或字典错配问题）。最具现实收益的仍是**官方三档异构混搭 + 自家校准 NNCF INT8 + 必要时领域微调/蒸馏**：DET 主导页优先测 `tiny DET + small REC`；清晰印刷密集页可测 `tiny REC → small REC` 回捞（但需警惕高置信错字与手写暴跌）；手写质量优先页反而是 `small DET + medium REC`。 | 以 `small+small` 为质量基线，优先实测 `tiny DET + small REC`；对 `tiny→small` 级联与 NNCF INT8 用业务留出集（区分印刷/手写/数字/小字）严格验收。 |

## 二、第一性原理：29 号机硬件物理边界与现网瓶颈铁证

### 2.1 29 号机 CPU 硬件与容器物理约束（已观察事实）

| 维度 | 29 号机实测 / 官方规格 | 对优化设计的硬约束 |
|---|---|---|
| **CPU 型号** | `Intel Xeon Silver 4216 @ 2.10 GHz`（Cascade Lake-SP，Family 6 Model 85 Stepping 7），1 插槽、16 物理核 / 32 逻辑线程、1 NUMA 节点 | 无跨 NUMA 惩罚；`scaling_governor=performance`，实测运行频率 `2.38 ~ 2.55 GHz`（单核最高睿频 `3.20 GHz`） |
| **向量单元与指令集** | **每核仅 1 个 512-bit FMA（Port 0）**；支持 `AVX2 / FMA / AVX-512F,DQ,CD,BW,VL` + **`AVX-512_VNNI`** | ① FP32 下 AVX-512 与 AVX2 理论吞吐相同（`1×512b == 2×256b`；@2.1 GHz 基准 `67.2 GFLOP/s/核`，@2.5 GHz `80 GFLOP/s/核`）；② **无 `AVX-512_BF16`、无 `AMX`**，社区 BF16 加速方案（如 `ppocrv6-fast-cpu` fast 模式）在本机无效；③ **`INT8 VNNI (VPDPBUSD)` 是本机唯一的 4× 硬件倍率** |
| **Cache 与内存带宽** | `L1d 32 KiB/核`、`L2 1 MiB/核`、`L3 22 MiB` 共享；6 通道 DDR4-2400（理论 `115.2 GB/s`） | `29` 实测 1 线程 OpenBLAS SGEMM `1024³` = **`47.7 GFLOPS`**，1 线程 64 MB DRAM memcpy（R+W=128 MB）= **`19.3 GB/s`** |
| **容器配额与并发** | `cpu.max=400000 100000`（4 核时间份额，`cpuset=0-31`）、`memory.max=4 GiB`、`swap.max=4 GiB`；2 同步 Gunicorn Worker × ORT `intra=2, inter=1, spinning=0`、`CV2/BLAS=1` | 调大单请求线程数或增 Worker 会争抢同一 4 核配额，且每增一个 Python 进程约多占一份模型+运行时内存；容器历史内存峰值已达 `3.70 GiB` |

> **方法论提示**：单线程 SGEMM 与 memcpy 仅提供算力与单核带宽锚点，缺少模型实际 DRAM 访存流量时，不能直接用“名义 GFLOPs ÷ 理论峰值”推导出承诺性的整页加速倍数；完整 Roofline 需在同核数、同亲和性与业务负载下配合硬件计数器实测。

### 2.3 29 号机 ORT 1.20.1 算子级 Profiling 与整链路拆解（实测事实）

#### A. 端到端阶段拆解（`29` 实测 `00009282.jpg`，`350×350 → det 736×736`，`14` 框，总计 `885.9 ms`）

- **神经网络推理**：`det_ort 245.8 ms (27.7%)` + `rec_ort 605.6 ms (68.4%)` = **`851.4 ms`（`96.1%`）**。
- **全部非模型阶段合计**：**`34.5 ms`（`3.9%`）**，包括 `imdecode 1.1 ms`、`det_pre 11.3 ms`、`det_post 6.2 ms`、`crop_warp 1.6 ms`、`rec_pre 3.0 ms`、`rec_argmax_max 10.2 ms`（双遍扫描 `58.2 MB` logits）、`rec_ctc_py 1.1 ms`。

> **Profiling 口径修正说明**：初稿中统计 ORT JSON trace 时未过滤 `fence_before/after` 事件，导致打印的算子调用次数被放大 3 倍（如 `83` 个 Conv 显示为 `249`、`~91` 次实际布局重排显示为 `273`）。`fence` 本身耗时微秒级，因此上述**毫秒耗时与占比结论有效**；但后续阶段 0 复测时必须严格只统计预热后单次 `model_run` 内的 `*_kernel_time` 事件，并关闭 profiling 另测稳态 wall time。

## 三、四大方向深度技术分析（严格限定 PP-OCRv6 及同族变种）

### 3.1 ONNX 模型、输入形状与 ORT 运行时优化边界

1. **三类不同含义的“上限”**（不可混为一谈）：
   - **当前服务容量上界**：按现网双同步 Worker 均值 `5.821 s` 计，饱和理想完成率约 `2 / 5.821 = 0.344 req/s`（`20.6 次/分钟`）；若受 4 核配额约束，长期吞吐上界为 `4 / C`（`C` 为平均核秒/图），两者取低值。
   - **硬件算术尺度**：4 物理核 @2.1 GHz 满载 FP32 理论 `268.8 GFLOP/s`（@2.5 GHz `320 GFLOP/s`），`736×3168` DET（`49.33 GFLOP`）纯算术尺度约 `154 ~ 184 ms`，这只是量级参考，不构成工程硬下界；INT8 VNNI 走另一套内核，须独立实测。
   - **单项优化的阿姆达尔上限**：某阶段占比 $f$、加速 $s$ 倍，整页仅快 $\frac{1}{(1-f) + f/s}$。必须按实际业务图分布（稀疏题图 vs 长截图 vs 密集文档）逐页回放计算 P95，不能把不同图片或不同机器的倍数直接相乘。

2. **最值得优先验证的“减工作量”优化（注意精度权衡）**：
   - **稀疏宽条图 `DET min_side 736 → 640`**：`806×187` 题图在 `736` 下放大 15.5 倍面积，改 `640` 可直接减少 `24.5%` DET MACs；需重点验收小字、上下标与题号召回率。
   - **密集页 `REC minW 320 → 160`（而非直接砍到 64）**：
     - [onnxocr/predict_rec.py](../onnxocr/predict_rec.py#L298) 硬编码 `max_wh_ratio = 320/48`，使短行大量补零。
     - **实证警示（已修正初稿乐观估计）**：在 8 张样图 / 256 个固定裁片上实测，`minW 320 → 160` 识别总耗时降 **`31.4%`**（`8.740s → 5.994s`，其中 73 行表格从 `2.172s → 1.198s` 且文字 100% 一致），但 **256 行中有 `14` 行文字发生变化、`4` 行跨过 `score=0.5` 留框线**；继续降到 `96/64` 仅多省 `5.6%~6.8%` 却会压缩窄图的 CTC 时间步（相邻重复字符需要 blank）。
     - **策略**：优先测 **`minW = 160`**（长行保持自然宽度、独立分批），用人工真值裁决变化行，不盲目下探到 `64`。
   - **词表静态裁剪与图尾 ArgMax（理性降级为“特定场景可选项”）**：
     - `small REC` 最后 `MatMul (120→18710)` 占名义 MAC `8.2%`、实测耗时 `7.0%`。即使按 `tiny` 词表（6,904 字，全部包含在 `small` 18,708 字典内）裁掉 63% 类别，按阿姆达尔定律对 `REC` 的单独加速上限也仅 **`~1.046×`**（约 `-4.4%`），且**删除类别会改变 Softmax 分母、漂移 `0.5` 留框判定与级联阈值**。
     - 图尾直接接 `ArgMax + GatherElements`（保留 `Softmax`）虽能把单批输出从 `17.96 MB` 压到 `2.88 KB`，但实测并无单图加速（反从 `180.2 → 188.1 ms`）；而若删除 `Softmax` 直接用 `max(logits)` 会破坏 [onnxocr/rec_postprocess.py](../onnxocr/rec_postprocess.py#L98-L109) 的概率置信度语义（精确 Top-1 概率仍需 `exp(max - logsumexp)` 全词表归约）。
     - **策略**：通用中文/未知字段保持完整 18,708 词表；仅在**明确限定字符集**（如纯数字/固定编码字段）且能重校准阈值时才启用词表裁剪。
   - **Arena Shrink 分阶段对照（不可盲关）**：因 29 号机历史内存峰值已达 `3.70 GiB`（余量仅 `0.30 GiB`），10 月 28 日历史对照也证明 arena 收缩对空闲内存压降显著（4 Worker 空闲 PSS 从 `4,143 → 1,602 MiB`）。若尝试关闭 `REC` 收缩（仅保留 `DET` 收缩），必须同步观测 cgroup RAM 峰值、swap 与 major page faults，`REC` 返回张量大小不能代表其内部激活高水位。

### 3.2 CPU 推理框架横评：谁在 Xeon Silver 4216 上最强？

ONNX 只是图交换格式，同一份 `PP-OCRv6` 权重在不同执行引擎下的算子融合、内存布局与指令集利用率差异巨大：

| 候选引擎 / 实现 | 公开 CPU 对照依据 | 对 29 号机（Xeon 4216 AVX-512 VNNI）的适配评估 | 试验优先级 |
|---|---|---|---|
| **Intel OpenVINO CPU（原生 FP32 & NNCF INT8）** | 官方 Xeon 8350C（`arXiv:2606.13108` Table 9，200 图）：`small` `0.59s` vs ORT `0.61s` (`1.03×`)，`tiny` `0.20s` vs `0.22s`，`medium` **`1.40s` vs `3.31s` (`2.36×`)**；`ppocrv6-fast-cpu`（34 图 FP32）：OpenVINO `1,458 ms` vs ORT `1,965 ms` (`1.35×`) | 底层 `oneDNN` 原生支持 `nChw16c` 块格式上的 `Conv+Bias+GELU+Add` 融合，有望消除我们在 `29` 上观测到的 ORT `12.2% Reorder + 7.7% GELU` 断层；更关键的是自带 **`nncf.quantize_with_accuracy_control`**，可自动保护敏感层并释放 4216 的 **INT8 VNNI**。**注意**：4216 无 BF16，保存 IR 需显式 `compress_to_fp16=False` | **P0（首选验证）** |
| **`RapidAI/RapidOCRLite` (`exact` 模式，C++)** | 作者 x86 AVX-512 8 vCPU 同 SHA `small` 对照 RapidOCR+ORT 1.31.0：212 页整图 `387.4 → 203.4 ms`（**`1.90×`**），**`small DET` `280.4 → 134.5 ms`（`2.08×`）**，单行 REC `6.3 → 7.0 ms`；212 页文字 100% 一致（`fast` 模式有 113/212 页文字变化，不可用） | **DET 主导场景的强力黑马**！需在 `29` 同 4 核配额、锁定 CPU-only `exact` 与相同权重/字典下复测，并单独检查密集页的 `REC` 是否回退；甚至可探索 `DET` 与 `REC` 异构选型 | **P0（同批验证）** |
| **新版 ORT CPU EP / ORT `OpenVINO EP` / `oneDNN EP`** | 现网为 `ORT 1.20.1`，社区已到 `1.23+/1.31+` | 升级 ORT 版本零架构改动成本；若保留 ORT 会话层则可条件追加 OpenVINO EP / oneDNN EP（须检查子图切分与 CPU fallback 开销） | **P0（零成本对照）/ P1** |
| **Paddle Inference (`paddle_static` + `oneDNN/MKLDNN`)** | 官方 Xeon 8350C：`small` `0.79s`（慢于 ORT `0.61s` 与 OpenVINO `0.59s`），`medium` `2.05s` | 依赖体积重（~2 GB）、内存偏大，仅作为官方原版参考对照，不作为 4 GiB 生产首选 | **P1（参考对照）** |
| **`Avafly/PaddleOCR-ncnn-CPP` (C++ + NCNN)** | 社区 Xeon VPS 复杂图：`small` `1,590 ms` / **峰值内存 `351.4 MB`**，`tiny` `420 ms` / **`156.7 MB`**（注意其默认配置为 `max_side=768` + 开方向 + 逐行并行，与现网口径不同） | **极端内存敏感场景的备选**；接入测试前必须对齐 DET 输入尺寸、关闭方向分类并按同并发测 cgroup 峰值 | **P2（内存优先时追加）** |
| **Alibaba MNN** | RapidOCR macOS 模块测：`small DET` `192.6 ms`（居中），`small REC` `44.7 ms`（显著慢于 OpenVINO `12.3 ms` 和 ORT `15.9 ms`） | ARM 移动端强项，x86 Xeon 上 `REC` 明显落后，仅可作 DET 备选 | **P2（备选）** |

### 3.3 定制开发与 Rust / C++ 的理性投入边界

1. **不要为了“提速单图推理”而用纯 Rust 重写通用引擎**：
   - `29` 与本地实测均证明，神经网络推理占端到端 `90% ~ 96%`，全部 Python/OpenCV/NumPy/后处理仅占 `4% ~ 10%`。
   - **纯 Rust 通用引擎（如 `tract` / `candle`）** 缺乏 Intel AVX-512 VNNI JIT 微核与 `Conv+GELU+Add` 融合，运行 PP-OCRv6 反而显著慢于 OpenVINO / ORT。
2. **Rust 生态已有两个可直接检验价值的 PP-OCRv6 标杆**：
   - **`GreatV/oar-ocr` (v0.11.0，Rust + ORT)**：其 `small DET/REC` 权重 SHA 与本仓完全一致；经典 OCR 底层走 ORT（支持配置 OpenVINO EP），适合用于量化“把 Python 服务壳换成 Rust 壳”在解码、裁片、拼批、JSON 与内存上的真实净收益（测试前须将其默认检测长边 `960`、REC 批量 `4` 对齐到现网口径）。
   - **`qinwenhui/qppocr`（纯 Rust 专用 PP-OCRv6 AVX2/NEON 内核）**：非通用框架，专门解析 v6 ONNX 并手写 SIMD 内核。作者在 16 逻辑核 x86 上测 `small` 热态约 `250 ms`；但注意其 README 列出的 `small` 字典摘要（`118d0f07...`）与本仓（`b5f2bfe2...`）**不一致**，接入测试前必须逐索引核对 blank/空格/字符映射！
3. **验证“单进程共享模型”无需先重写 Rust**：
   - Python Gunicorn 之所以内存翻倍，是因为同步多进程每进程各持一份权重与运行时。**选定 OpenVINO 后，直接在 Python 内用单进程共享 `CompiledModel` + 多个 `InferRequest` / `AsyncInferQueue`**，在同一 4 核 / 4 GiB 预算下对比双 Worker，即可低成本验证单进程共享模型能省多少 RAM（注意：权重可共享，但各路并发的中间激活与缓冲仍占内存，不能提前假设必压到 350–600 MiB）。
   - 顺手可做的 Python 侧确定性小优化：① `/pdf/ocr`（[flask_server.py](../flask_server.py#L140-L160)）消除 `PIL → PNG → cv2.imdecode` 无意义编解码往返；② 水平框快速裁切路径（[onnxocr/utils.py](../onnxocr/utils.py#L16-L57)）：仅在四角严格整数、图内、轴对齐且旋转等价时走切片（差 1 像素斜框即回退 `warpPerspective`，实测耗时占比小，按长图实际占比决定优先级）。

### 3.4 PP-OCRv6 同族变种、量化与预制权重审慎评估

#### A. 同族异构混搭与级联路线

1. **`tiny DET + small REC`（最高性价比优先试）**：
   - 在 `DET` 主导的稀疏题图和 `4640×1088` 超长图上，`tiny DET` 计算量仅为 `small DET` 的约 **`1/3.5`**，同时完整保留 `small REC` 的 18,708 词表与手写/印刷识别力。
   - **验收重点**：检查 `tiny DET` 是否漏掉小字、题号、上下标，以及框边界变化对 `small REC` 的连锁影响；先独立换检测器并采用 `tiny` 推荐阈值（`det_db_box_thresh=0.40`，对比 `small` 的 `0.45`），再组合缩放。
2. **`tiny REC` 初识 + `small REC` 低置信度回捞（条件采用，须防三大陷阱）**：
   - **实证数据（已修正初稿假设）**：在 8 图 / 256 个固定 `small DET` 裁片上实测，全量 `small REC` 需 `4,614 ms`、`tiny REC` 需 `1,025 ms`：
     - 阈值 `0.85`：回捞 `30.5%`（78/256），REC 总耗时降 `51.9%`，但直接接受行中有 **`28` 行与 `small` 不同**；
     - 阈值 `0.90`：回捞 **`35.2%`**（90/256，远高于理论拍脑袋的 10%–20%），耗时降 `46.7%`，仍有 **`20` 行直接接受分歧 + `1` 行回捞重拼批分歧**（其中 `tiny` 最高置信度高达 **`0.999187`** 仍与 `small` 不同！）；
     - 阈值 `0.98`：回捞 `51.6%`，耗时降 `24.7%`，仍有 `8 + 5 = 13` 行分歧。
   - **结论**：该方案**仅适合清晰中文印刷体为主的密集页切片**；对含手写体/复杂数字/外文的流量不可盲上，且双识别模型常驻内存也须纳入 4 GiB 峰值验收。
3. **`small DET + medium REC`（手写/关键字段质量优先切片）**：
   - 若业务中手写体或关键数值错误代价高，可在困难行上做 `small → medium` 升级（中文手写 `57.6% → 62.1%`），并评估额外内存与延迟成本。

#### B. 自家校准 INT8（AVX-512 VNNI）vs 第三方预制派生权重

- **为什么不直接拿社区预制 INT8 上线？**

| 公开 v6 派生候选 | 实测 / 源码核查现状 | 结论 |
|---|---|---|
| `byrizki/rusto-models`（v6 tiny/small INT8 ONNX） | `tiny DET` 有 83 个 `ConvInteger`，但 **`REC` 仍有 37 个浮点 Conv**（仅 2 个 `MatMulInteger`）；作者在 i7-1185G7 上测得 INT8 (`1,822 ms`) 反而慢于 FP32 (`1,128 ms`) | 仅作加载对照，**不可直接上线** |
| `circulus/PP-OCRv6-*-int8-ov`（OpenVINO IR INT8） | 固化静态 `DET 640²`、`REC 48×320`，破坏长截图与变长行策略；且 `tiny` 包内字典为 18,708 行，与模型 6,906 输出类别**错配**；缺少中文业务校准依据 | 仅作加载对照，**不可直接上线** |
| `Kellenok/PP-OCRv6_manga` v0.3 | 基于官方 `tiny DET + small REC` 微调（中文行裁片 CER `2.28%`），漫画字体版面与通用文档/试题不同 | 仅参考其“混搭 + 领域微调”范式 |

- **正确的 INT8 落地方法**：以本仓 FP32 为真源，**先独立量化 `small DET`，再独立量化 `small REC`**，使用自家业务脱敏校准集（覆盖宽条题图、长截图、密集表格、空白、手写、小字，且与最终留出验收集严格按文档来源隔离）：
  1. **首选 OpenVINO + `nncf.quantize_with_accuracy_control`**（`drop_type=DropType.ABSOLUTE, max_drop=0.005`，`validation_fn` 分别用 DET Hmean / REC 整行精确率），保存 IR 时显式 `compress_to_fp16=False`，并用 OpenVINO 执行图确认 `AVX-512 VNNI` 实际命中比例与敏感层回浮位置；
  2. **同步对照 ORT 静态 S8S8 QDQ**（per-channel 权重量化），对比实际 VNNI 内核耗时、反量化开销与精度退化。
- **远期质量-速度破局点（领域微调与蒸馏）**：官方 `v3.7.0` 已开放 3 档 DET/REC 共 6 份训练权重与配置。若上述无训练优化触顶后仍存在特定字体/手写瓶颈，可在 `29` 的 RTX 4090 上离线用自家真值 + `medium` 教师微调/蒸馏 `small` 或 `tiny`（**仅在离线训练使用 4090，线上推理仍 100% 纯 CPU**），从而在更小网络或更低输入分辨率下保住业务精度。

## 四、29 号机分阶段实证与落地实施计划

### 4.1 冻结测试资产与严格验收口径

1. **三类分层数据集（校准集与最终留出集严格按文档来源隔离）**：
   - **短宽稀疏组**：43 张历史 `806×187` 题图（重点看 `DET` 与小字召回）；
   - **超长截图组**：4 张 `tmppic`（`1550×6664`，重点看 `4640×1088` 内存峰值、DET+REC 平衡与长图漏行）；
   - **密集/多态组**：补齐近期真实业务切片（密集表格、低清小字、手写体、长行/重复数字、空白页、多页 PDF）。
2. **三层回放定位差异**：① 固定 `DET` NCHW 张量纯测检测引擎；② 固定基线 `DET` 裁片纯测识别引擎；③ 走完整旧 HTTP 接口 `/predict/ch_pp-ocrv3` 验收端到端协议、框坐标、行序、分数与业务 `status`。
3. **统一观测指标与噪声控制**：
   - 质量：DET Hmean / 小字召回、REC 同框 CER / 整行精确率 / 关键数字与字段 exact、`score >= 0.5` 留框翻转数；
   - 性能：P50 / P95 / P99（标明样本数 N）、持续图/s、CPU 核秒/图、cgroup `memory.peak` / PSS / swap / major page faults / CPU throttling 增量；
   - 噪声控制：隔离容器、固定权重与字典 SHA、单次预热后交错反转次序跑 ≥3 轮；若增益小于同配置重复运行抖动，保留更简单实现。

### 4.2 按 ROI 与依赖排序的五阶段试验路线

| 阶段 | 试验范围与变量控制 | 晋级门禁与交付物 |
|---|---|---|
| **Stage 0 · 29 基线与止血** | ① 经授权修复现网容器 `--health-cmd` 引号错误；② 在隔离同配容器（`2w×2t`，`--cpus=4 --memory=4g`）对冻结样本集采集全套质量、分段耗时（仅计 `*_kernel_time`）、CPU 核秒与 cgroup 内存/swap 基线 | 拿到各类业务图的精确 DET/REC 占比、准确率和基线 P50/P95，作为后续全部实验的 A 组 |
| **Stage 1 · 同权重换引擎（零精度妥协）** | 锁定 `small` ONNX SHA 与预后处理，在 4 核 / 4 GiB 下逐一对比：① 现网 `ORT 1.20.1`；② 新版 `ORT CPU EP`；③ 原生 **OpenVINO CPU FP32**（`INFERENCE_NUM_THREADS=2, NUM_STREAMS=1, f32`，分别记冷编译、命中 `CACHE_DIR` 与稳态）；④ **`RapidOCRLite exact`**；⑤ Paddle `oneDNN` 参考。`DET` 与 `REC` 分开评选 | **同权重门槛**：回归集整页文字、行序、留框判定与基线一致；若引入新依赖，须在同 4 核下使 P95 或持续吞吐提升 **`>= 15%`** 且另一项不回退、4 GiB 内零 OOM/无持续换页增长 |
| **Stage 2 · 减工作量与并发调优** | 每次只改一项：① 稀疏组 `DET min 736 → 640`；② 密集组 `REC minW 320 → 160`（长行独立成批、测试 `batch 1/4/6/8`）；③ A/B 测试关闭 `REC` arena shrink；④ 并发配比对比 `1w×4t` / `2w×2t` / `4w×1t`（评估内存）及 **Python OpenVINO 单进程共享 `CompiledModel` + 双 `InferRequest`** | 人工真值裁决 `640` / `W160` 的文字与留框变化；用单进程共享实验定量回答“内存能否从 `3.70 GiB` 显著下降”，再决定是否进入 Rust 化 |
| **Stage 3 · VNNI INT8 与 v6 同族混搭** | 各自独立配对后再组合：① `small DET` NNCF 精度受控 INT8（`max_drop=0.005`）+ `small REC FP32`，对比 ORT S8S8 QDQ；② 固定裁片独立测 `small REC` INT8；③ **`tiny DET + small REC`**（调优 `box_thresh=0.40`）；④ 清晰印刷切片测 **`tiny REC → small REC` 实际重拼批回捞**（重点核查高置信分歧）；⑤ 手写切片测 `small DET + medium REC` | 产出“速度—精度”帕累托前沿组合表（各业务切片的得失量化）；若特定字段/手写仍有缺口，再启动 4090 离线微调/蒸馏或窄词表头 |
| **Stage 4 · 整机极限与服务化交付** | ① 在独立资源窗口对胜出的 1–2 组测 **`4 → 8 → 16` 物理核**（按 `lscpu -e` 绑物理核，再单独测 SMT 增益）；② 若 Stage 2/3 证明并发内存或前后处理成为新瓶颈，再推进 Rust（`oar-ocr` / `axum` + OpenVINO C-API）或 C++ 服务化；③ 若存在可信版式/ROI 或持续小批 backlog，再叠加 ROI 裁区或跨请求微批 | 最终交付三组可承诺的实测“上限”数字：① **4 核下最低单页/P95**；② **4 核 SLO 下最大持续图/s**；③ **独占 16 物理核极限图/s**（均附核秒/图、峰值内存、质量指标与回滚镜像方案） |

### 7.4 Stage 1 选型结论与下一步建议

1. **`ORT 1.32.0` 是 Stage 1 唯一“零风险立即可上线”的明确胜出项**：相比现网 `ORT 1.20.1`，在**全部 10 张图上 100% 逐字完全一致（`sim=1.0000`）**、零新增依赖的前提下，单图延迟下降 **`8% ~ 33%`**、单轮总 CPU 下降 **`17.0%`**、`4 GiB` 并发吞吐提升 **`+10.1% ~ +12.5%`**、并发峰值内存再降 **`394 MB`（`2,886.6 → 2,492.7 MB`）**。
2. **`OpenVINO 2026.4.1 FP32` 未通过 Stage 1“同权重引入新依赖（`>=15%`）”门槛**：
   - 在固定/窄幅场景（`layout_cdla` 共享单进程 `0.389 rps`、`sparse/table/715873`）稳态仅快 `ORT 1.32.0` 约 `6% ~ 10%`；但在变宽长图（`tmppic_1/3/4`）下因 `REC` 自由动态宽度触发频繁内部内存重分配与形状特化，**`cpu_system` 飙至 `43.88s`（vs ORT 1.32 `4.36s`）**、`tmppic_1` 并发吞吐反降 **`2.68×`**（`0.124` vs `0.332 rps`）。
   - **第一性原理内存验证结果**：`small` 权重总共仅 `31 MB`，并发峰值主要由 `4640×1088` 激活与动态形状缓冲主导，因此 OpenVINO 单进程共享模型在 `6 GiB` 下峰值仍达 **`3,954 MB`**（仅比双进程 `4,157 MB` 省 `203 MB`），远高于带 `Arena Shrink` 的 `ORT 1.32.0`（`2,493 MB`）。OpenVINO 若要胜出，必须留待 **Stage 3** 配合 **NNCF INT8 VNNI + 离散 REC 宽度分桶** 重新对决。
3. **`RapidOCRLite 5.0.0a16 exact` 在 29 号机 4 核配额下被淘汰**：尽管在 `00009282`/`table`/`layout_cdla` 墙钟较快，但原因在于其 `PPOCR_BENCH_THREADS=2` 仅限制了 `cpu_info.threads`，内部并行仍吃到 `~3.5~3.7` 核（引发 **196 次 cgroup 限流、浪费 `72.0s` 限流时间、总 CPU 高出 `ORT 1.32.0` 达 `1.70×`**）；同时大分辨率 `DET (4640×1088)` 比 `ORT 1.32.0` 慢 **`1.68×`**（`3.0s` vs `1.78s`），且 `6/10` 图与基线文本存在差异（`sim=0.9514 ~ 0.9903`）。
4. **明确下一步动作**：
   - **短期低成本落地（可选上线）**：将 `requirements.compat-cpu.txt` 的 `onnxruntime==1.20.1` 升级为 **`onnxruntime==1.32.0`** 并重打生产镜像替换。
   - **进入 Stage 2 / Stage 3（决定最终极致形态）**：在 `ORT 1.32.0` 与 `OpenVINO（离散宽度分桶）` 上开展核心高杠杆验证——① `Arena Shrink` 仅对 `DET` 大图触发；② `REC minW 320 → 160`、稀疏图 `DET min 736 → 640`；③ **`tiny DET + small REC`**；④ **NNCF 精度受控 INT8 VNNI vs ORT S8S8 QDQ**。

  1. **`2w×2t` 是 4 核下最均衡配比**：`1w×4t` 因单模型 `intra=4` 并行衰减损失 `16%~22%` 吞吐；`4w×1t` 仅在满 4 并发密集图上略高 `2.3%`，但低并发长图 P50 恶化 `74%`（`10.44s` vs `6.00s`）且闲置 RSS 翻倍（`2,047 MB`）。
  2. **跨引擎混跑并发收益被线程池与内存抵消**：尽管 `Hybrid OV det_ac + ORT QDQ REC` 单进程仅 `19.0s`，但在 4 核 `2w×2t` 并发下因 OpenVINO TBB 与 ORT Eigen 线程池混用导致单波仅用到 `~2.87` 核（`37.21s / 12.985s`）且双运行时常驻内存飙至 `3.25 ~ 3.65 GB`，反而不如单引擎纯 ORT 的 **`0.4819 rps` / `2.97 GB`**！

### 8.7 分级落地选型与 Stage 4 入口（经 8.8 节 155 图验证后更新）

1. **Tier 0（唯一推荐立即上线，100% 通用/手写/试卷零损）**：升级 `onnxruntime==1.32.0`，保持 `small DET/REC FP32`、`2w×2t` 与全量 `Arena Shrink`（`+10~12.5%` 并发 RPS，`-394 MB` 并发内存）。
2. **Tier 1（仅限纯印刷/非关键数字路由的端到端条件选项，不推荐手写与考试图）**：`ORT 1.32.0 + small DET FP32 + rec_qdq_u8s8 + shrink=det_2mp` 在密集印刷页（`layout_cdla`）并发可达 `0.4819 rps`（`+43.9%` vs 现网）；但经 8.8 节 **155 图大样本验证**，所有 PTQ 配方在中文手写体上的 `subCER` 仍达 **`10.53% ~ 11.11%`**，手写数学数字串一致率仅 `36.84% ~ 44.74%`，故**不能用于含手写/学生作业/试卷的默认流量**。若业务后续必须在纯 CPU 上同时压低手写体 REC 耗时与守住 CER，需走 **4090 离线 QAT（量化感知训练）** 或 **`ORT 1.32.0` + 业务脱敏蒸馏**。
3. **Stage 4 入口**：针对通用/手写/试卷流量，下一步应基于 **Tier 0 (`ORT 1.32.0 FP32`)** 在 `29` 号机测试 **`4 → 8 → 16` 物理核**（`lscpu -e` 绑核，`4w×2t` / `8w×2t`）的纯 CPU 无损吞吐天花板；若需进一步降低单次 `DET` 延迟且对极小字不敏感，也可单独对比 `OV small_det_ac INT8 + ORT FP32 REC`（无 REC 量化损失）在 16 核下的表现。

- **四大工程判据结论**：
  1. **10 图均值具有误导性，155 图揭露真实代价**：在 `LOCAL-ESSAY-001` 等中文手写长卷上，所有 PTQ 配方均反复出现实质同形/形近字错配（`紧盯→紧目`、`田貌→因貌/因`、`民生服务→民生眼务`、`治理→若理/范理`、`浓厚→农厚`、`部署→部`），且置信度同步下降（如 `0.976→0.899`），整个 `ALL_HANDWRITTEN` 切片 `subCER` 高达 **`10.53% ~ 11.11%`**，手写数学数字串一致率仅 `36.84% ~ 44.74%`。
  2. **保护 `CTC MatMul` 与全部 `MatMul` 并不能根治手写退化**：`no_ctc` 与 `convonly` 仅将手写 `subCER` 从 `11.11%` 微幅拉回到 `10.80%`（代价是 `REC` 加速比从 `1.58×` 降至 `1.49×`），证明主要量化误差源于 SVTR 主干 `57` 个卷积对笔画连笔、模糊特征的低比特表达损失，而非仅仅源自末尾分类头。
  3. **`S8S8` 在 Cascade Lake 上彻底失去加速价值**：`qdq_s8s8_minmax_convonly` 虽仅微降 `0.27%` 手写 CER，但因 `AVX-512 VNNI` 原生 `vpdpbusd` 为 `U8×S8` 设计，ORT `S8S8` 引入符号位修正开销后反而比 `FP32` 慢 **`18%`（`0.84×`）**。
  4. **最终决策**：**现网生产与含手写/考试场景只允许部署无损的 `ORT 1.32.0 FP32`（Tier 0）**；若后续确实需要让 `REC` 在 `INT8` 下兼顾手写与数字精度，必须引入带人工真值的 **QAT（量化感知训练）** 或放弃 REC 量化。
